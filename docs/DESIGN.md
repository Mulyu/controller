# 設計メモ: Android仮想コントローラー

壁打ちで固まった設計判断のまとめ。実装の詳細はコード側のコメントを参照。

## 要件と前提の是正

元の要件は次の2つ:

1. 常駐し、他アプリの上にフロート表示してタッチコントロールをラップする
2. USB/Bluetoothコントローラーとして認識させ、ゲームにデフォルトのタッチUIを無効化させる

要件2はそのままでは成立しない。`BluetoothHidDevice` も USB gadget HID も
「自機が他のホストに対してデバイスを名乗る」API であり、自分自身をホストに
することはできない。

一方、対象ゲームが**ネイティブでパッド対応している**ことが確認できたため、
要件1と2は「タッチ注入」ではなく「パッド入力への置換」という1つの仕組みで
同時に満たせる。

```
オーバーレイのスティック/ボタン → 仮想ゲームパッド(uinput) → ゲームがパッドを認識
                                                          → ゲームが自分でタッチUIを消す
```

これにより `TouchSink`（仮想タッチスクリーン）や、オーバーレイと注入タッチ
座標の衝突といった当初想定していた難所が丸ごと消える。オーバーレイは全画面
を覆ってタッチを吸い切ってよい設計になった。

## 権限モデル: Shizuku 前提

`/dev/uinput` を開くには shell または root 権限が要る。今回は **Shizuku
前提**で確定。Accessibility (`dispatchGesture`) はタッチ注入はできても
「パッドが存在する」ことにはならず、要件2を満たせないため不採用（フォール
バックとしても持たない判断）。

現行の Shizuku API (`dev.rikka.shizuku`) は任意コマンド実行用の
`newProcess` を公開しておらず、`UserService`（AIDL）を shell/root UID の
別プロセスとして起動する方式が正となる。この UserService プロセス自体が
shell 権限で動くため、内部で `ProcessBuilder` を使って `uinput` コマンドを
起動できる。JNI/ioctl は不要（v0時点）。

## 仮想デバイス: Xbox 360 パッドを名乗る

Android に `Vendor_045e_Product_028e.kl`/`.idc` が同梱されているため、
`Microsoft X-Box 360 pad` (vid=0x045e, pid=0x028e, bus=usb) を名乗ると
keylayout が確実に当たり、パッドをホワイトリストしているゲームにも通り
やすい。`BTN_MODE`（ガイドボタン）は システム動作を誘発しうるため公開しない。

デッドゾーンは `flat` ではなく入力側 (`StickMapper`) で処理する。uinput
デバイス自体は `flat=0` の線形デバイスとして登録し、Android の
InputReader 側で勝手に丸められないようにする。

## オーバーレイ: コントロールごとに個別ウィンドウ

タッチ注入をしない設計になったことで、「オーバーレイの当たり判定に注入
タッチが返ってくる」問題自体は消えたが、それでも全画面ひとつの
touchable window を貼ると、コントロール外の全タッチも吸い込んでしまい
ゲーム側の操作ができなくなる。

そのため `OverlayService` は **コントロールごとに小さな `WindowManager`
ウィンドウを個別に追加**する（スティック1枚 + ボタン4枚 + トグルハンドル
1枚 = 6ウィンドウ）。コントロールが存在しない領域には何もウィンドウが
無いので、タッチは自然に下のアプリへ素通りする。

常時表示のトグルハンドルで「キャプチャの一時停止」ができるようにし、
ゲーム内メニューやOSダイアログの操作を可能にしている（サービス自体は
止めない）。

## v0 のスコープと未検証事項

このセッションには Android SDK・実機・エミュレータが無く、`:core`
（純Kotlinのパッド状態→uinputイベント変換ロジック）のみユニットテストで
実際に検証できた。`:app` 側は API 仕様に基づいて実装したが実機未検証。
README.md の "Known gaps" に検証すべき項目をまとめてある。最重要なのは:

- `uinput` コマンドの JSON スキーマが実機のAOSPバージョンと一致するか
- shell UID が実機で `/dev/uinput` を開けるか
- 対象ゲームが起動後にパッド接続を再スキャンするか（しない場合、パッドを
  先に生やしてからゲームを起動する導線が v1 で必須になる）

## ロードマップ

- **v0（本PoC）**: Shizuku + `uinput` CLI、固定レイアウト（スティック1+
  ボタン4）、パッドテスター画面
- **v1**: JNI バックエンド（`uinput` CLI 経由より低遅延）、レイアウト
  エディタ、スティック感触調整UI、プロファイル保存
- **v2**: ゲーム別プロファイル自動切替、ジャイロ→右スティック、連射/
  マクロ、root バックエンド
